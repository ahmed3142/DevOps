Part Four

Environments, Infrastructure and Containers

Infrastructure as code, immutability, defence against drift, and the orchestration decision.

4.1 The problem with the current servers

The two production servers are pets: named, hand-reared and understood by one person. Their real configuration exists only in the running machine and in Sam's memory, and neither copy can be reviewed, compared or restored. Every manual fix applied under incident pressure widens the gap between the two servers, and between production and staging. This is the mechanism behind failures that reproduce in one environment and not another, and no amount of care will remove it. The remedy is to make infrastructure an output of a build rather than an accumulation of history.

4.2 Declarative code rather than a deployment script

Nimbus already has automation in deploy.sh. The distinction that matters is that the script is imperative: it lists steps from an assumed starting state, so it is not idempotent, and run against a drifted host it produces a result nobody predicted. Terraform is declarative. It describes the intended end state and computes the difference, so it converges on the same result from any starting point.

The governance consequence is at least as valuable as the technical one. A terraform plan executed in a pull request is a reviewable diff of what is about to change in production, before it changes. Infrastructure decisions become peer-reviewed, timestamped and attributable. That is a stronger control than a change-approval meeting, because it is precise, automatic and produces a record without anyone writing one.

4.3 Structure, state and environment parity

Terraform is organised as reusable modules for network, service, database and observability, consumed by thin per-environment configurations that differ only in variable values such as instance size and replica count. Staging is therefore not a hand-built approximation of production but the same definition with smaller numbers, which makes parity structural rather than a matter of discipline. State is stored remotely with locking and never on a laptop; it is both the record of what exists and a file containing sensitive values, so it is encrypted, access-controlled and versioned.

4.4 Immutability and drift

Servers are not modified in place. A change produces a new image and a new instance, and the old instance is destroyed. Rollback then becomes redeployment of the previous known-good artefact, and disaster recovery becomes a rebuild from code rather than the restoration of a machine nobody can reproduce. Drift is defended in four layers, because detection on its own does not prevent anything.

4.5 Containers as the unit of deployment

The application is packaged as a container image, and that image is the deployable unit on a developer laptop, in CI, in staging and in production. The Dockerfile in the supporting repository is a three-stage build: dependencies installed strictly from the lockfile, the application compiled, and a runtime stage containing only the standalone server on a minimal base image running as an unprivileged user. This buys three things at once. The runtime image is small and therefore quick to pull, it excludes build tooling and source and so presents less attack surface, and because the build is driven by a lockfile and a pinned base digest the same inputs produce the same image. That reproducibility is what makes an artefact safe to promote without retesting it.

4.6 Orchestration

Kubernetes would give Nimbus declarative rollouts, self-healing, autoscaling and service discovery, and it is where most industry attention sits. It is still the wrong choice for this team this year.

Managed container runtime now; Kubernetes when it is earned.

Kubernetes is not a single tool but an operational surface: cluster upgrades, networking, ingress, role-based access control, storage classes and a control plane to fund. Operating it competently requires at least one engineer with deep expertise, which would reproduce Nimbus's defining problem, a bus factor of one, at a higher level of abstraction and with worse failure modes. A managed container service provides declarative service definitions, health-based rolling deployments and autoscaling from the same image the pipeline already builds, for a fraction of that operational surface.

The decision is time-bound rather than permanent. It is revisited when any of four conditions holds: more than roughly ten services, ownership split across multiple teams, a real requirement for traffic shaping such as canary or a service mesh, or the hire of a dedicated platform engineer. Naming the conditions turns a preference into a decision a successor can evaluate.

Environments follow the artefact. Compose runs it locally, CI runs it in ephemeral containers, and staging and production are built from the same Terraform modules, with per-pull-request preview environments added once the foundations are stable.
