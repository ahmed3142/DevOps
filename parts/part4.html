Part 4

Environments, Infrastructure and Containers

Lectures 7, 8 and 9 — infrastructure as code, containerisation, orchestration and drift.

4.1 From pets to cattle

Nimbus's two servers are pets: named, hand-reared, irreplaceable, and understood by one person. Their true configuration exists in only two places — the running machine and Sam's memory — and neither can be reviewed, diffed or restored. Every manual fix applied under incident pressure widens the gap between the two servers and between production and staging. This is the mechanism that produces "it worked in staging", and it cannot be solved by being more careful.

The remedy is to make the infrastructure a build output rather than a historical accident. Every environment is defined in Terraform, the definition is reviewed like application code, and servers are replaced rather than repaired.

4.2 Why declarative code beats a deployment script

Nimbus already has automation: deploy.sh. The distinction that matters is that the script is imperative — it describes a sequence of steps from an assumed starting state — while Terraform is declarative, describing the desired end state and computing the difference. The script is therefore not idempotent: running it twice does not produce the same result twice, and running it against a host that has drifted produces something nobody predicted. A declarative tool converges on the same state from any starting point.

The governance consequence is the more valuable one. terraform plan executed in a pull request produces a reviewable diff of what is about to change in production, before it changes. Infrastructure decisions become peer-reviewed, timestamped and attributable, which is a stronger control than any change-approval meeting because it is precise and automatic. The illustrative snippet in the supporting repository shows the shape: a single definition, parameterised by environment, with mandatory ownership and cost-centre tags.

4.3 Structure, state and parity

Terraform is organised as reusable modules — network, service, database, observability — consumed by thin per-environment configurations that differ only in variable values such as instance size and replica count. Staging is therefore not a hand-built approximation of production but the same definition with smaller numbers, so environment parity is achieved by construction rather than by discipline. State is stored remotely with locking, never on a laptop: state is both the source of truth for what exists and a file containing sensitive values, so it is encrypted, access-controlled and versioned.

4.4 Immutability and the defence against drift

Servers are never modified in place. A change produces a new image and a new instance, and the old one is destroyed. Rollback becomes redeployment of the previous known-good artefact, and disaster recovery becomes a rebuild from code rather than a restore of a machine nobody can reproduce. Drift is then defended in four layers, because detection alone is insufficient.

4.5 Containers as the unit of deployment

The application is packaged as a container image, and that image is the deployable unit everywhere: on a developer's laptop through Compose, in CI, in staging and in production. The Dockerfile in the supporting repository is a three-stage build — dependencies installed strictly from the lockfile, the application compiled, and a final runtime stage containing only the standalone server on a minimal base image, executing as an unprivileged user. Multi-stage building matters for three reasons at once: the runtime image is small and therefore fast to pull and cheap to store; it excludes build tooling and source, reducing the attack surface; and because the build is driven by a lockfile and a pinned base digest, the same inputs produce the same image. Reproducibility is what makes an artefact trustworthy enough to promote without retesting.

4.6 Orchestration: the case against Kubernetes today

Kubernetes would give Nimbus declarative rollouts, self-healing, autoscaling and service discovery, and it is where the industry's attention sits. It is still the wrong choice for this team this year.

Design decision — managed container runtime now, Kubernetes when it is earned

Kubernetes is not one tool but an operational surface: cluster upgrades, networking, ingress, RBAC, storage classes and a control plane to fund. Running it competently requires at least one engineer with deep expertise — which would recreate Nimbus's defining problem, a bus factor of one, at a higher level of abstraction and with far worse failure modes. A managed container service delivers declarative service definitions, health-based rolling deployments and autoscaling for a fraction of that operational surface, and it maps cleanly onto the same image the pipeline already builds.

The decision is therefore time-bound rather than permanent, with explicit triggers for revisiting it: more than roughly ten services, ownership split across multiple teams, a genuine need for traffic shaping such as canary or service mesh, or the hire of a dedicated platform engineer. Naming the triggers converts a preference into an architectural decision record that a successor can evaluate.

Environments follow the artefact: Compose locally, ephemeral containers in CI, staging and production defined by the same Terraform modules, with per-pull-request preview environments as a later addition once the foundations are stable.
