Part Two

Version Control and Collaborative Workflow

Branching strategy, review as knowledge transfer, release tagging and traceability.

2.1 The chosen workflow

Nimbus adopts trunk-based development with short-lived branches. Every change is cut from main, lives on a branch for no more than two days, and returns through a pull request that requires a passing pipeline and one approving review. The trunk is protected: no direct pushes, no force-pushes, and no merge while the build is red. The supporting repository demonstrates this shape, with four feature branches merged into a protected trunk and released as an annotated tag.

2.2 Alternatives considered

GitFlow is the obvious incumbent and the wrong fit here. Its develop, release and hotfix branches earn their keep when a vendor ships versioned software to customers who decide when to upgrade. Nimbus runs one production instance shared by every customer, so those branches provide no isolation while formalising the long-lived-branch behaviour that already produces a seventeen-day lead time.

Committing directly to the trunk without review, the purest form of trunk-based development, is rejected for a different reason. Nimbus's defining risk is that one engineer holds all production knowledge. A pull request is the cheapest knowledge-transfer mechanism available: it obliges a second person to read every change and it records why the change was made. Review here is redundancy in the team's understanding rather than a check on trust.

Batch size is the mechanism.

The branching model matters mainly because it caps how much changes at once. Twelve small merges a week carry less risk than one large merge a month: each contains fewer changes, is easier to review honestly, is faster to diagnose when it fails and is simple to revert. This is why lead time and change failure rate tend to improve together rather than trade against each other.

2.3 Conventions and releases

Commits follow the Conventional Commits specification. The benefit is machine readability rather than tidiness: a structured history lets changelogs and version numbers be generated instead of negotiated. Merge commits are kept deliberately, because a merge groups a feature's commits into one revertible unit, while squashing discards the intermediate steps that make a bisect useful. Releases are annotated semantic-version tags on the trunk, so a version number identifies one commit, one image and one set of passing tests.

2.4 Traceability

An unbroken chain connects a business request to a running process. The ticket identifier appears in the branch name, carries into the commit messages, is referenced by the pull request that records the review, is captured by the release tag, is baked into the image digest built from that tag, and is finally reported by the service itself: the /api/health endpoint returns the version it is executing, as shown in Figure 6. Any environment can therefore be traced to the commit that produced it without asking anyone.

That chain also serves as the audit trail. It answers what changed, when and who approved it in seconds rather than through a search of chat history, and it produces the evidence a security questionnaire will later require at no additional cost.
