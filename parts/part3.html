Part 3

CI/CD Pipeline and Quality Strategy

Lectures 4, 5 and 6 — continuous integration, automated testing, and release strategy with rollback.

3.1 Pipeline shape

Figure 2 sets out the target pipeline. A push triggers static analysis, unit tests and a production build; a container image is then built once and tagged with the commit SHA. That image is deployed to staging automatically, exercised by integration and smoke tests, and only then promoted to production. Promotion re-uses the identical artefact — nothing is rebuilt per environment.

Build once, deploy many is the single most important property of the design. If each environment compiles its own artefact, the thing tested in staging is not the thing running in production, and the team is left arguing about a difference no one can reproduce. This directly retires Nimbus's most common failure mode. The supporting repository implements the first half of this pipeline today: every push runs lint, unit tests and a production build, and a dependent job builds the container image from the same commit.

3.2 Automated testing

Testing is organised as a pyramid, costed by execution time because feedback speed is the property being bought.

Table 2 — Target test portfolio
LayerScopeVolumeBudgetRuns
UnitPure logic, validation, permissions~1,200< 2 minEvery push

ContractBilling and email provider boundaries~15< 1 minEvery push
End-to-endCritical journeys: sign-up, note CRUD, sharing, billing~10< 6 minPost-deploy to staging

Nimbus will be tempted into the inverted pyramid — the "ice-cream cone" — because it has no unit tests today and browser tests appear to cover more ground per test written. That temptation must be resisted. End-to-end tests are slow, environmentally fragile, and locate failures poorly: a red browser test says the checkout is broken, while a red unit test says which function returns the wrong value. A suite dominated by end-to-end tests eventually becomes flaky, and a flaky suite is worse than no suite because it teaches engineers to re-run failures rather than read them.

3.3 Quality gates

Each gate has a defined threshold and a defined consequence, so that "quality" is enforced by the pipeline rather than negotiated in a meeting.

  • Lint and type checking — any error fails the build.
  • Unit and integration tests — all must pass; coverage is governed by a ratchet that forbids a decrease rather than a fixed percentage target. A fixed number such as eighty per cent invites tests written to satisfy the number instead of the risk, and it punishes the small, well-tested change that touches a poorly covered file.
  • Dependency and container scanning — critical or high severity vulnerabilities with an available fix block the merge; lower severities open a tracked issue.
  • Infrastructure policy checks — Terraform plans are checked against policy before they can be applied (Part 5).
  • Pipeline duration — a hard ten-minute budget from push to feedback. When the pipeline exceeds it, that is logged as a defect against the platform, because a slow pipeline is routed around, and a gate that is routed around is not a gate.

3.4 Release strategy and rollback

Production releases use blue-green deployment. Two identical environments sit behind a load balancer; the new version is deployed to the idle one, smoke-tested against real infrastructure with no customer traffic, and then made live by shifting the load balancer. The previous environment is kept warm for thirty minutes, so a rollback is a traffic shift measured in seconds rather than a redeployment measured in hours.

Design decision — why not canary

Canary releasing is the more sophisticated option and is deliberately deferred. It requires weighted traffic routing, per-cohort metrics and enough request volume to reach a statistically meaningful judgement quickly; at Nimbus's traffic a one per cent canary would take days to produce a trustworthy signal. More fundamentally, a canary is only as good as the observability used to evaluate it, and that observability does not yet exist. A canary without it is simply a slower outage. Canary becomes the right answer once the SLOs in Part 5 are in place and traffic has grown — a sequencing decision, not a rejection.

Blue-green costs roughly double compute for the duration of a release window. For a stateless web tier that is a few euro per release, which is materially cheaper than one hour of an outage, and the cost disappears when the old environment is retired. The honest limitation is that blue-green protects the application tier and not the database, which leads to the practice that actually makes rollback possible.

Expand and contract migrations. Schema changes are split across releases: first an additive change that both the old and new code can tolerate, then the code that uses it, then a backfill, and only in a later release the removal of the old column. Without this discipline every rollback plan is a fiction, because code can be reverted in seconds and a destructive migration cannot be reverted at all.

Feature flags decouple deployment from release, so incomplete work can be merged and shipped while remaining invisible to customers. This is what allows small batches without exposing half-finished features, and it provides a second, instantaneous rollback mechanism that does not require a deployment at all.

Finally, rollback is rehearsed. A deliberate rollback is executed in staging every month and the runbook is corrected wherever it proved wrong. An untested rollback procedure is a hope, not a plan, and an incident is the worst possible moment to discover the difference.
