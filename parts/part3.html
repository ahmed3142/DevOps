Part 3

CI/CD Pipeline and Quality Strategy

Lectures 4, 5 and 6 — continuous integration, automated testing, and release strategy with rollback.

3.1 Pipeline shape

Figure 2 sets out the target pipeline. A push triggers static analysis, unit tests and a production build; a container image is then built once and tagged with the commit SHA. That image deploys automatically to staging, is exercised by integration and smoke tests, and is only then promoted to production — re-using the identical artefact, with nothing rebuilt per environment.

Build once, deploy many is the most important property of the design. If each environment compiles its own artefact, the thing tested in staging is not the thing running in production, and the team is left arguing about a difference nobody can reproduce. This retires Nimbus's most common failure mode. The supporting repository implements the first half of this pipeline today: every push runs lint, unit tests and a production build, and a dependent job builds the image from the same commit.

3.2 Automated testing

Testing is organised as a pyramid, costed by execution time because feedback speed is the property being bought.

Table 2 — Target test portfolio

UnitPure logic, validation, permissions~1,200< 2 minEvery push

ContractBilling and email provider boundaries~15< 1 minEvery push
End-to-endCritical journeys: sign-up, note CRUD, sharing, billing~10< 6 minPost-deploy to staging

Nimbus will be tempted into the inverted pyramid — the "ice-cream cone" — because it has no unit tests today and browser tests appear to cover more ground per test written. End-to-end tests are, however, slow, environmentally fragile and poor at locating failures: a red browser test says checkout is broken, while a red unit test says which function returns the wrong value. A suite dominated by them becomes flaky, and a flaky suite is worse than none, because it teaches engineers to re-run failures rather than read them.

3.3 Quality gates

Each gate has a defined threshold and consequence, so quality is enforced by the pipeline rather than negotiated in a meeting.

  • Lint and type checking — any error fails the build.
  • Unit and integration tests — all must pass; coverage is governed by a ratchet forbidding a decrease rather than a fixed percentage. A fixed target such as eighty per cent invites tests written to satisfy the number rather than the risk, and penalises the small, well-tested change that touches a poorly covered file.
  • Dependency and container scanning — critical or high severity findings with an available fix block the merge; lower severities open a tracked issue.
  • Infrastructure policy checks — Terraform plans are evaluated against policy before they may be applied (Part 5).
  • Pipeline duration — a hard ten-minute budget from push to feedback; exceeding it is logged as a platform defect, because a slow pipeline gets routed around, and a gate that is routed around is not a gate.

3.4 Release strategy and rollback

Production releases use blue-green deployment. Two identical environments sit behind a load balancer; the new version is deployed to the idle one, smoke-tested against real infrastructure with no customer traffic, then made live by shifting the balancer. The previous environment stays warm for thirty minutes, so rollback is a traffic shift measured in seconds rather than a redeployment measured in hours. The cost is roughly double compute during the release window — a few euro for a stateless web tier, and materially cheaper than an hour of outage.

Design decision — why not canary

Canary releasing is the more sophisticated option and is deliberately deferred. It requires weighted traffic routing, per-cohort metrics and enough request volume to reach a statistically meaningful judgement quickly; at Nimbus's traffic a one per cent canary would take days to produce a trustworthy signal. More fundamentally, a canary is only as good as the observability used to evaluate it, and that observability does not yet exist — a canary without it is simply a slower outage. Canary becomes the right answer once the objectives in Part 5 are in place and traffic has grown. This is a sequencing decision, not a rejection.

Blue-green protects the application tier but not the database, which leads to the practice that actually makes rollback possible. Expand-and-contract migrations split schema changes across releases: first an additive change both old and new code tolerate, then the code that uses it, then a backfill, and only in a later release the removal of the old column. Without this discipline every rollback plan is fiction, because code reverts in seconds and a destructive migration cannot be reverted at all.

Feature flags decouple deployment from release, so incomplete work can be merged and shipped while remaining invisible to customers. This permits small batches without exposing half-finished features and provides a second, instantaneous rollback mechanism requiring no deployment. Finally, rollback is rehearsed monthly in staging and the runbook corrected wherever it proved wrong: an untested rollback is a hope rather than a plan, and an incident is the worst moment to learn the difference.
