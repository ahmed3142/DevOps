Part Three

Continuous Delivery and Quality

Pipeline design, the test portfolio, quality gates, automation priorities, release and rollback.

3.1 Pipeline design

Figure 2 sets out the target pipeline. A push runs static analysis, unit tests and a production build, then builds a container image tagged with the commit SHA. That image deploys automatically to staging, is exercised by integration and smoke tests, and is promoted to production unchanged.

Building once and deploying many times is the most important property of the design. When each environment compiles its own artefact, the version tested in staging is not the version running in production, which is the source of the environment differences in the scenario. The supporting repository implements the first half of this pipeline today, as Figure 3 shows.

3.2 Test portfolio

Tests are organised as a pyramid and budgeted in execution time, because feedback speed is what the portfolio is bought for.

Table 2 — Target test portfolio

UnitLogic, validation, permissions~1,2002 minEvery push
IntegrationAPI against a real database in a container~1505 minEvery push
End-to-endSign-up, note CRUD, sharing, billing~106 minAfter staging deploy

Nimbus will be tempted into the inverted pyramid, because it has no unit tests and browser tests appear to cover more ground each. But end-to-end tests are slow, fragile and poor at locating faults: a failing browser test reports that checkout is broken, while a failing unit test names the function. A suite dominated by them becomes flaky, and a flaky suite teaches engineers to re-run failures instead of reading them.

3.3 Quality gates

Each gate has a defined threshold and consequence, so quality is enforced by the pipeline rather than negotiated in a meeting.

  • Lint and type checking: any error fails the build.
  • Unit and integration tests: all must pass. Coverage is governed by a ratchet that forbids a decrease, rather than a fixed percentage, because a fixed target invites tests written to satisfy the number instead of the risk.
  • Dependency and container scanning: critical or high findings with an available fix block the merge; lower severities open a tracked issue.
  • Pipeline duration: a ten-minute budget from push to feedback. Exceeding it is recorded as a platform defect, since a slow pipeline gets worked around and a gate that is worked around is not a gate.

Automation competes for the same hours as product work, so candidates are scored rather than chosen by enthusiasm.

The last row is the useful one. Automating the production approval gate saves almost nothing while a quarter of changes fail, and the human pause costs less than the incidents it prevents; it becomes worth removing once earlier work has made releases unremarkable. Two candidates are staged until there is telemetry to drive them: machine-assisted test selection, running only the tests a change can plausibly break, and anomaly detection across metrics and logs, which is how a cloud-native estate with more signals than engineers keeps alert volume manageable. Both need a baseline, and without one they would automate guesswork.

3.5 Release and rollback

Production releases use blue-green deployment. Two identical environments sit behind a load balancer. The new version is deployed to the idle one, smoke-tested against real infrastructure with no customer traffic, then made live by shifting the balancer. The previous environment stays warm for thirty minutes, so rollback is a traffic shift measured in seconds rather than a redeployment measured in hours. The cost is roughly double compute during the release window, a few euro for a stateless tier, against an hour of outage.

Canary is deferred, not rejected.

Canary releasing requires weighted traffic routing, per-cohort metrics and enough request volume to reach a trustworthy judgement quickly. At Nimbus's traffic a one per cent canary would take days to produce a usable signal. A canary is also only as good as the observability used to evaluate it, and that observability does not yet exist, so today it would amount to a slower outage. Canary becomes the right choice once the objectives in Part 5 are running and traffic has grown.

Blue-green protects the application tier but not the database, which leads to the practice that makes rollback genuine. Expand-and-contract migrations split a schema change across releases: an additive change both old and new code tolerate, then the code that uses it, then a backfill, and only later the removal of the old column. Without this, rollback plans are fiction, because code reverts in seconds and a destructive migration does not revert at all. Feature flags decouple deployment from release, keeping batches small and providing a second rollback path that needs no deployment. Rollback is rehearsed monthly in staging, since an untested rollback is an assumption rather than a plan.
