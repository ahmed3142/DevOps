Part Five

Observability, Security and Reliability

Telemetry, service level objectives, shifted-left security, incident response and recovery.

5.1 Observability rather than monitoring

The four-hour restore time follows from how Nimbus observes production. Monitoring answers questions decided in advance, such as whether CPU is high; observability lets an engineer ask a question nobody anticipated.

Three signals are instrumented. Metrics follow RED for services and USE for resources, alongside business measures such as sign-ups completed; a technically healthy system that has quietly stopped accepting registrations is still an outage. Logs are structured JSON carrying a correlation identifier, centralised and tiered by retention so cost scales with value rather than traffic. Traces use OpenTelemetry, propagated from the edge; without them, a report that the application is slow is an opinion rather than a location. A fourth signal is added deliberately: deployments, flag changes and infrastructure applies are annotated onto the same dashboards, because the first useful question in an incident is what changed.

5.2 Objectives and the error budget

Indicators are defined on user journeys rather than infrastructure: success rate and 95th-percentile latency for creating and reading notes, and success rate for sign-in. The objective is 99.9 per cent availability measured monthly, permitting roughly forty-three minutes of failure. That target is chosen rather than inherited: each additional nine multiplies engineering cost by an order of magnitude, and the difference between 99.9 and 99.95 per cent is invisible to customers while the difference in cost is not.

The budget settles an argument that is otherwise settled by seniority.

The remaining tenth of a per cent is an error budget governed by policy. While the budget is healthy, changes deploy freely and promotion is automated. Below twenty-five per cent remaining, feature work pauses in favour of reliability work. When it is exhausted, a change freeze applies until a review and its actions are complete. Speed against stability stops being a matter of opinion and becomes a rule agreed in advance and enforced by data.

Alerting follows burn rate rather than raw thresholds: a fast burn consuming two per cent of the monthly budget within an hour pages a human; a slow burn raises a ticket.

5.3 Security in the pipeline

Security today is a late review, if it happens at all, with credentials in .env files and chat history. Each control moves into the pipeline, where a failure is a build result rather than an audit finding.

  • Secrets move to a managed store, injected at runtime and rotated on a schedule, and CI authenticates through OIDC federation so the pipeline holds no long-lived cloud credentials. Pre-commit scanning stops secrets entering history at all, which matters more than rotation, because Git history is permanent and a committed key must be treated as compromised.
  • Supply-chain controls cover dependency scanning, a software bill of materials per build, signed images and an admission rule that only signed images deploy.
  • Policy as code encodes rules that currently live in people's heads, such as no public storage and mandatory ownership tags, evaluated against the Terraform plan at merge.
  • Compliance evidence becomes a by-product rather than a project. Approvals, pipeline logs, signed artefacts and applied plans are already immutable records, so a security questionnaire is answered with a query rather than a scramble.

5.4 Reliability, incidents and recovery

Resilience is designed in rather than added afterwards. Every outbound call carries a timeout, because an unbounded call is how one slow dependency exhausts a thread pool and turns partial failure into total. Retries use exponential backoff with jitter, since synchronised retries turn a brief wobble into a self-inflicted denial of service. Circuit breakers isolate a failing dependency, bulkheads stop one tenant consuming shared capacity, idempotency keys make retried writes safe, and degradation beats failure: serving notes read-only while billing is unavailable beats an error page. Health-check-driven replacement and autoscaling handle routine cases without waking anyone, and a release rolls back automatically if burn spikes.

When a human is required, the process is defined in advance: a documented on-call rotation across the team rather than an implicit dependency on one person, a runbook for every alert, and clear incident roles. Reviews are blameless, held within five working days, and their actions tracked as backlog items whose completion rate is measured, because a review that produces no change is theatre.

Recovery targets are explicit: a one-hour recovery time objective and a fifteen-minute recovery point objective, met with encrypted backups, point-in-time restore and multi-availability-zone redundancy. Restores are tested quarterly, since a backup never restored is an assumption rather than a control. Multi-region active-active is rejected for now, because it multiplies cost for a failure mode far rarer than those actually causing Nimbus outages.
