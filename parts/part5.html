Part 5

Observability, Security and Reliability

Lectures 10, 11 and 12 — telemetry, DevSecOps, service level objectives and recovery.

5.1 Observability, not just monitoring

Nimbus's four-hour restore time is a direct consequence of how it observes production. Monitoring answers questions decided in advance — is CPU high, is the host up — whereas observability lets an engineer ask a question nobody anticipated. Today the team can only interrogate failures it already thought of, so every novel incident begins with an SSH session and a search through unstructured logs.

Three signals are instrumented. Metrics follow RED for services (rate, errors, duration) and USE for resources, alongside business measures such as sign-ups completed — a technically healthy system that has silently stopped accepting registrations is still an outage. Logs are structured JSON carrying a correlation identifier, centralised, sampled at volume and tiered by retention so cost scales with value rather than traffic. Traces use OpenTelemetry, propagated from the edge, because vendor-neutral instrumentation keeps the data portable; without them "the application is slow" is an opinion rather than a location. A fourth signal is added deliberately: change events. Deployments, flag flips and infrastructure applies are annotated onto the same dashboards, because the first useful question in any incident is what changed — and answering it from memory is how Nimbus loses its first hour.

5.2 Service level objectives and the error budget

Indicators are defined on user journeys rather than infrastructure: success rate and 95th-percentile latency for note creation and retrieval, and success rate for sign-in. The objective is 99.9% availability measured monthly, permitting roughly forty-three minutes of failure. That target is chosen rather than inherited: each additional nine multiplies engineering cost by roughly an order of magnitude, and the difference between 99.9% and 99.95% is invisible to customers while the difference in cost is not.

The mechanism that resolves speed versus stability

The remaining 0.1% is an error budget governed by policy rather than judgement. While the budget is healthy, changes deploy freely and automatically. Below twenty-five per cent remaining, feature work pauses in favour of reliability work. When it is exhausted, a change freeze applies until a review and its actions are complete. This converts the perennial argument between shipping and stability — usually settled by whoever is most senior in the room — into a rule agreed in advance and enforced by data.

Alerting follows burn rate rather than raw thresholds: a fast burn consuming two per cent of the monthly budget within an hour pages a human, a slow burn raises a ticket. Threshold alerts on CPU correlate poorly with customer harm, and the resulting noise trains engineers to ignore alerts — the failure mode that turns a detectable incident into a long one.

5.3 Shifting security left

Security today is a late review, if any, with credentials in .env files and Slack history. The strategy moves every control into the pipeline, where a failure is a build result rather than an audit finding.

  • Secrets move to a managed store, injected at runtime and rotated on schedule, and CI authenticates to the cloud through OIDC federation so the pipeline holds no long-lived credentials at all. Pre-commit scanning stops secrets entering history in the first place — prevention matters more than rotation, because Git history is permanent and a committed key must be treated as compromised.
  • Supply chain controls: dependency scanning, a software bill of materials per build, signed images, and an admission rule that only signed images deploy. Patch updates merge automatically when the pipeline is green, keeping the habit cheap enough to sustain.
  • Policy as code encodes rules that used to live in people's heads — no public storage, no unrestricted administrative access, every resource tagged with an owner and cost centre — evaluated against the Terraform plan at merge time.
  • Compliance evidence becomes a by-product rather than a project: approvals, pipeline logs, signed artefacts and applied plans are already immutable records, so a security questionnaire is answered with a query rather than a fire drill — which matters directly to the enterprise deals the funding round should unlock.

5.4 Reliability, incident response and recovery

Resilience is designed in, not added afterwards. Every outbound call carries a timeout, because an unbounded call is the classic mechanism by which one slow dependency exhausts a thread pool and turns a partial failure into a total one. Retries use exponential backoff with jitter, since synchronised retries convert a brief wobble into a self-inflicted denial of service. Circuit breakers isolate failing dependencies, bulkheads stop one tenant consuming shared capacity, idempotency keys make retried writes safe, and graceful degradation beats failure — serving notes read-only while billing is down beats an error page. Health-check-driven replacement and autoscaling handle routine cases without waking anyone, and automated rollback triggers if error-budget burn spikes during a release.

When a human is needed the process is defined in advance: a documented on-call rotation across the whole team rather than an implicit dependency on one person; a runbook for every alert, with an alert lacking one treated as a defect; and clear incident roles so communication and investigation do not compete. Reviews are blameless, held within five working days, and their actions tracked as backlog items whose completion rate is measured — a review that produces no change is theatre.

Recovery targets are explicit: a one-hour recovery time objective and a fifteen-minute recovery point objective, met with automated encrypted backups, point-in-time restore and multi-availability-zone redundancy. Restores are tested quarterly, because a backup never restored is an assumption rather than a control. Multi-region active-active is deliberately rejected for now: it multiplies cost and complexity to address a failure mode far rarer than those actually causing Nimbus outages, and should be revisited only when enterprise contracts demand it. Game days begin modestly — terminating an instance in staging to prove the automation and runbooks work before an incident tests them.
