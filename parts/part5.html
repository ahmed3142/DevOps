Part 5

Observability, Security and Reliability

Lectures 10, 11 and 12 — telemetry, DevSecOps, service level objectives and recovery.

5.1 Observability, not just monitoring

Nimbus's four-hour restore time is a direct consequence of how it observes production. Monitoring answers questions decided in advance — is CPU high, is the host up — whereas observability is the property of a system that lets an engineer ask a question nobody anticipated. Today the team can only interrogate the failures it already thought of, so every novel incident begins with an SSH session and a search through unstructured logs.

Three signals are instrumented. Metrics follow RED for services (request rate, error rate, duration) and USE for resources (utilisation, saturation, errors), alongside business measures such as notes created per minute and sign-ups completed — a technically healthy system that has silently stopped accepting registrations is still an outage. Logs are emitted as structured JSON carrying a correlation identifier, centralised, sampled at volume and tiered by retention so that cost scales with value rather than with traffic. Traces are produced with OpenTelemetry and propagated from the edge, because vendor-neutral instrumentation keeps the data portable; without traces, "the application is slow" remains an opinion rather than a location.

A fourth signal is added deliberately: change events. Deployments, feature-flag flips and infrastructure applies are annotated onto the same dashboards, because the first useful question in any incident is what changed, and answering it from memory is how Nimbus currently loses its first hour.

5.2 Service level objectives and the error budget

Indicators are defined on user journeys rather than infrastructure: the success rate and 95th-percentile latency of note creation and retrieval, and the success rate of sign-in. The objective is 99.9% availability measured monthly, which permits roughly forty-three minutes of failure. That target is chosen rather than inherited: each additional nine multiplies engineering cost by roughly an order of magnitude, and for a small-business productivity tool the difference between 99.9% and 99.95% is invisible to customers while the difference in cost is not.

The mechanism that resolves speed versus stability

The remaining 0.1% is an error budget, governed by policy rather than judgement. While the budget is healthy, changes deploy freely and automatically. Below twenty-five per cent remaining, feature work pauses and reliability work takes priority. When the budget is exhausted, a change freeze applies until a review and its actions are complete. This converts the perennial argument between shipping and stability from a matter of opinion, usually settled by whoever is most senior in the room, into a rule agreed in advance and enforced by data.

Alerting follows burn rate rather than raw thresholds: a fast burn consuming two per cent of the monthly budget in an hour pages a human, while a slow burn raises a ticket. Threshold alerts on CPU produce noise that correlates poorly with customer harm, and noise trains engineers to ignore alerts — the failure mode that turns a detectable incident into a long one.

5.3 Shifting security left

Security today is a review performed late, if at all, with credentials in .env files on the servers and in Slack history. The strategy moves every control into the pipeline, where a failure is a build result rather than an audit finding.

  • Secrets move into a managed secret store, injected at runtime and rotated on a schedule. CI authenticates to the cloud through OIDC federation, so the pipeline holds no long-lived cloud credentials at all. Pre-commit scanning and push protection stop secrets entering history in the first place — prevention matters more than rotation here, because Git history is effectively permanent and a leaked key must be treated as compromised the moment it is committed.
  • Supply chain controls include dependency scanning, a software bill of materials generated for every build, cryptographic signing of images, and an admission rule that only signed images may be deployed. Patch-level dependency updates merge automatically when the pipeline is green, which keeps the update habit cheap enough to sustain.
  • Policy as code encodes the rules that used to live in people's heads — no publicly readable storage, no unrestricted administrative access from the internet, every resource carrying an owner and cost centre — and evaluates them against the Terraform plan at merge time.
  • Compliance evidence is then a by-product rather than a project. Approvals, pipeline logs, signed artefacts and applied plans are already immutable records; an auditor or an enterprise customer's security questionnaire is answered with a query rather than a fire drill, which matters directly to the enterprise deals the funding round is meant to unlock.

5.4 Reliability, incident response and recovery

Resilience is designed into the application, not added afterwards. Every outbound call carries a timeout, because an unbounded call is the classic mechanism by which one slow dependency exhausts a thread pool and converts a partial failure into a total one. Retries use exponential backoff with jitter, since synchronised retries turn a brief wobble into a self-inflicted denial of service. Circuit breakers isolate a failing dependency, bulkheads prevent one tenant's load from consuming shared capacity, idempotency keys make retried writes safe, and graceful degradation is preferred to failure — serving notes read-only while the billing provider is unavailable is a far better outcome than an error page. Health-check-driven replacement and autoscaling handle the routine cases without waking anyone, and an automated rollback triggers if error-budget burn spikes during a release.

When a human is needed, the process is defined in advance: a fair, documented on-call rotation across the whole team rather than an implicit dependency on one person; a runbook for every alert, with an alert lacking one treated as a defect; and clear incident roles so that communication and investigation do not compete. Reviews are blameless and held within five working days, and their actions are tracked as real backlog items — the completion rate of those actions is measured, because a review that produces no change is theatre.

Recovery targets are stated explicitly: a one-hour recovery time objective and a fifteen-minute recovery point objective for production data, met with automated encrypted backups, point-in-time restore and multi-availability-zone redundancy. Restores are tested quarterly, since a backup that has never been restored is an assumption rather than a control. Multi-region active-active is deliberately rejected at this stage: it multiplies cost and complexity to address a failure mode far rarer than the ones that actually cause Nimbus outages, and it should be revisited only when enterprise contracts demand it. Game days begin modestly, by terminating an instance in staging to prove the automation and the runbooks work before an incident tests them for the first time.
