A.3 The container and infrastructure artefacts

Dockerfile. The image is built in three stages. The first installs dependencies strictly from the lockfile, the second compiles the production bundle, and the third copies only the standalone server onto a minimal Alpine base and runs it as an unprivileged user. Separating the stages keeps build tooling and source out of the shipped image, which reduces both its size and its attack surface, and pinning the base image by digest alongside the lockfile means the same inputs produce the same image every time. That reproducibility is what allows one artefact to be promoted from staging to production without being rebuilt or retested, which is the direct answer to the environment drift described in Part 1.

Compose file. This defines how the container runs, as code rather than as a command someone remembers: the port mapping, a restart policy, and a health check that polls /api/health every thirty seconds. The health check is the part that matters operationally, because it distinguishes a container that is running from a service that is actually answering. The same signal is what an orchestrator or deployment script uses to decide whether a new release is healthy or should be rolled back, so the local definition and the production behaviour are checked the same way.

Terraform snippet. The file under infra/ is illustrative and is not applied to any live account, but it shows the intended shape. The provider and its version are pinned so that a later run cannot silently change behaviour, the environment is a variable so that staging and production come from one definition, and every resource carries Owner, CostCentre and Environment tags. Those tags are what make the FinOps reporting in Part 6 possible, since an untagged resource cannot be attributed to anyone and therefore never gets cleaned up.
