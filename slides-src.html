The organisation

Fifteen people, four hundred customers, two hand-built servers

A company whose delivery process was designed for three people in one room.

  • Two EC2 instances configured by hand over SSH and edited in place ever sinceTheir real configuration exists only in the machine and in one engineer's memory
  • Deployment is a person — Sam runs deploy.sh from a laptopEvery release queues behind one calendar

Why now

A funding round and a doubling of the engineering team are coming. Technical due diligence asks how often you ship and how fast you recover — and the honest answers are currently embarrassing.

Part 1 · Diagnosis

Waste, a knowledge silo, and where CALMS stops helping

  • Waiting dominates — queues, not effort
  • Three handoffs per change, each discarding context
  • Partially done work in three-week branches
  • Relearning in every outage — no runbooks
  • Bus factor of one — the silo is knowledge, not departments

A critique of CALMS

CALMS describes a destination, not a route. It supplies no sequence — so teams start with Automation because tooling is tangible, automating a process nobody has measured. It is also silent on cost and security, which is why FinOps and DevSecOps had to be bolted on.

So we invert it

Measurement and Sharing first. Automation follows from them, not before.

Part 2 · Version control

Trunk-based development on a protected trunk

  • Branches live under two days, merged by pull requestBatch size is the real lever: twelve small merges beat one large one
  • Not GitFlow — release and hotfix branches earn their keep only when customers choose when to upgradeNimbus runs one shared instance; GitFlow would formalise the disease
  • Not direct-to-trunk eitherReview is the cheapest knowledge transfer available to a bus-factor-of-one team

Traceability chain

ticket → branch → commit → pull request → release tag → image digest → /api/health reports the running version.

Any environment traces back to the exact commit that produced it — without asking anyone. That chain is also the audit evidence.

Part 3 · Quality

Gates with thresholds, not opinions

  • ~1,200 unit tests under 2 minutes
  • ~150 integration tests against a real database
  • ~10 end-to-end journeys only — post-deploy
  • Coverage ratchet, not a fixed 80%A fixed number invites tests written to satisfy the number
  • Ten-minute pipeline budgetA slow pipeline gets routed around, and a gate routed around is not a gate

The trap we are avoiding

With no unit tests today, browser tests feel like faster coverage — the ice-cream cone. But they are slow, fragile and locate failures poorly, and a flaky suite teaches engineers to re-run failures instead of reading them.

Part 3 · Release

Blue-green now, canary when it is earned

  • Blue-green: deploy to idle, smoke test, shift trafficRollback is a traffic shift in seconds, not a redeployment in hours
  • Expand-and-contract migrationsCode reverts in seconds; a destructive migration never does — this is what makes rollback real
  • Feature flags decouple deploy from release
  • Rollback rehearsed monthlyAn untested rollback is a hope, not a plan

Why not canary

Canary needs weighted routing, per-cohort metrics and enough traffic for a fast statistical signal — at Nimbus's volume, a 1% canary takes days to say anything trustworthy.

More importantly, a canary is only as good as the observability judging it. Without that, it is simply a slower outage. Sequencing, not rejection.

Part 4 · Orchestration

We are not adopting Kubernetes — yet

The reasoning

Kubernetes is not one tool but an operational surface: cluster upgrades, networking, ingress, RBAC, storage classes, a control plane to fund.

Running it competently needs one engineer with deep expertise — which recreates our defining problem, a bus factor of one, at a higher altitude and with worse failure modes.

A managed container runtime gives declarative services, health-based rolling deploys and autoscaling for a fraction of that surface.

Triggers to revisit

The decision is time-bound, not permanent. We reopen it when any of these becomes true:

  • More than roughly ten services
  • Ownership split across multiple teams
  • Real need for traffic shaping — canary, service mesh
  • A dedicated platform engineer is hired

Part 5 · Security & recovery

Shift security left; rehearse recovery

  • OIDC federation — the pipeline holds no long-lived cloud credentialsPre-commit scanning stops secrets entering history; Git history is permanent
  • SBOM, signed images, admission policy
  • Policy as code turns compliance findings into build failures
  • Evidence as a by-productApprovals, logs, signed artefacts and applied plans answer the questionnaire
  • Timeouts, backoff with jitter, circuit breakers, bulkheadsGraceful degradation beats an error page
  • RTO 1 hour · RPO 15 minutes, restores tested quarterlyA backup never restored is an assumption, not a control
  • Multi-AZ yes, multi-region noMultiplying cost for a failure mode rarer than the ones actually hurting us

Honest trade-off

At our size, engineering time costs more than infrastructure. Three weeks of effort to save a few hundred euro a month is a bad trade. And the real defect in the scenario is not a missing tool — it is a missing owner.

Part 6 · Leading the change

The technical plan is the straightforward half

Sam is the most important stakeholder

The single expert can veto this programme, and their standing derives from being indispensable. A plan that quietly removes that status will be resisted — whatever its engineering merits.

Frame it as a promotion: Sam owns the platform, with the pipeline and infrastructure code as their product. Then measure the bus factor — engineers who can independently deploy and recover production. It starts at one.

  • Start with pain the team already feelsOpening with policy enforcement reads as bureaucracy
  • Speak each audience's languageBoard: delivery risk and unit cost. Team: no weekend releases.
  • A fifth of each iteration for debt, with its monthly cost stated
  • “You build it, you run it” — only with authority and time, otherwise it is just extra pager duty

Part 6 · Roadmap

Twelve months, five stages, deliberate order

StageFocusExit condition
0 · Weeks 1–2Measure — instrument the metrics, change nothing elseA baseline the team agrees with
1 · Weeks 3–8Make it repeatable — trunk, CI, containers, staging in TerraformAny engineer can produce a deployable artefact
2 · Months 3–5Make it safe — blue-green, telemetry, SLOs, on-callWeekly releases without a release weekend
3 · Months 6–9Make it secure and economical — gates, OIDC, FinOps, tested restoresQuestionnaire answered from evidence
4 · Months 9–12Make it self-service — previews, progressive delivery, game daysDaily deployment as routine

Measurement precedes change because unevidenced improvement cannot be funded. Repeatability precedes safety because automated rollback is meaningless without a reproducible artefact to roll back to.

Closing

Speed and stability are not opposites

The assumption this strategy is designed to disprove.

The practices that make delivery fast — small batches, automated verification, reproducible environments, fast feedback — are the same ones that make it safe, because a small, tested, reversible change is both quicker to ship and easier to diagnose when it fails.
